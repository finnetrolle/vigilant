# VIG-05-08: Нагрузочный тест PERF-01

**Статус:** Ready for implementation
**Epic:** [EPIC-05](../../epics/epic_05_v0_hardening.md)
**Ветка:** Производительность > нагрузочный тест
**Зависит от:** нет
**Предпочтительный порядок (не блокировка):** после issue явных таймаутов - длительный прогон не должен зависеть от библиотечных дефолтов
**Блокирует:** нет
**Оценка:** 4-6 инженерных дней
**Уверенность:** Medium

## Результат

Воспроизводимый Gatling-нагрузочный тест измеряет `proxy_overhead`
(`latency_through_vigilant - latency_direct_to_upstream`) при 2 000 RPS на
p99 и либо подтверждает `PERF-01` (<= 2 мс), либо фиксирует полный отчёт с
причиной отклонения и измеренным baseline.

## Требования

`PERF-01`, `PERF-06`, критерий готовности v0 №6.

## Критерии готовности

- [ ] Gatling-сценарий в репозитории; запуск одной командой, документирован в
  README (или docs/).
- [ ] Сценарий сравнивает direct-to-upstream baseline и путь через gateway на
  одном и том же upstream в одном прогоне.
- [ ] Профиль включает streaming и non-streaming запросы; размеры тел, число
  соединений и распределение фиксируются в конфигурации сценария.
- [ ] Выполняются требования `PERF-06`: прогрев JVM до устойчивого состояния,
  длительность прогона, характеристики оборудования и профиль записаны вместе с
  результатом.
- [ ] Итоговый отчёт зафиксирован в репозитории: measured `proxy_overhead` p99
  при 2 000 RPS + методика, либо отчёт об отклонении с причиной и baseline.
- [ ] Тест не входит в `./gradlew build` (не ломает CI), запуск - явно.

## Не входит

`PERF-02..05` (plugin workers - их ещё нет), автоматический SLO-gate в CI,
JMH-микробенчмарки (отдельная работа), нагрузочное тестирование stage 1.

## Рекомендуемые решения внутри issue

- Upstream - локальный echo-сервер с управляемой задержкой, чтобы измерять
  именно overhead gateway, а не апстрим.
- Отчёт - markdown в `docs/` с параметрами прогона и сырыми числами;
  Gatling-отчёт генерируется в `build/`.
