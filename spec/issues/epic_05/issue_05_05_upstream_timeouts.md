# VIG-05-05: Явные таймауты upstream-клиента

**Статус:** Done
**Epic:** [EPIC-05](../../epics/epic_05_v0_hardening.md)
**Ветка:** Надёжность proxy > явные таймауты upstream-клиента
**Зависит от:** нет
**Предпочтительный порядок (не блокировка):** после issue стабильных proxy-ошибок - истекший таймаут должен отображаться стабильной proxy-ошибкой
**Блокирует:** нет
**Оценка:** 1-2 инженерных дня
**Уверенность:** High

## Результат

Upstream `WebClient` сконфигурирован явными таймаутами (connect, write,
response) и настройками pooling, задаваемыми через конфигурацию (env/file) с
дефолтами, безопасными для длинных LLM-стримов. Сейчас используется
`WebClient.of()` с библиотечными дефолтами.

## Требования

Раздел «Входит в v0»: connection pooling, backpressure, timeout и cancellation
propagation.

## Критерии готовности

- [x] Настройки таймаутов подключены к существующему механизму конфигурации
  (`env > file > defaults`, префикс `VIGILANT_`), включая дефолты.
- [x] Response timeout не убивает легитимный длинный стрим: принятая модель
  (рекомендованный baseline: idle-based timeout либо явный большой response
  timeout для стримов) зафиксирована и протестирована.
- [x] Истекший таймаут отображается клиенту стабильной proxy-ошибкой из
  VIG-05-01.
- [x] E2E-тест: зависший upstream прерывается по таймауту с малым тестовым
  значением, настроенным через env.
- [x] Unit-тесты загрузки и валидации новых параметров (отрицательные,
  нулевые, невалидные значения).
- [x] Дефолты и названия параметров задокументированы в
  `vigilant.conf.example` и README.
- [x] `./gradlew build` проходит.

## Итог проверки

Принята idle-based модель (пункт «если Armeria поддерживает»): дефолтный
response timeout Armeria покрывает ответ целиком и убил бы длинный LLM-стрим,
поэтому каждый полученный от upstream объект ответа сбрасывает дедлайн на
`now + response-timeout` (`TimeoutMode.SET_FROM_NOW`). Итоговая семантика
`vigilant.upstream-response-timeout` - время до первого объекта ответа плюс
максимальная пауза между объектами; общая длительность стрима не ограничена.

Названия параметров - плоские (`vigilant.upstream-connect-timeout` и т.д.),
env-имена соответствуют рекомендованным (`VIGILANT_UPSTREAM_CONNECT_TIMEOUT`
и т.д.) и наследуют существующий generic-механизм `VIGILANT_*` без
специального кода. Pooling: `maxNumConnections` в Armeria 1.41 отсутствует,
единственная pooling-настройка - `upstream-connection-idle-timeout`;
подтверждено E2E-тестом, что соединение с незавершённым ответом не считается
простаивающим. Покрытие: `AppConfigLoadingTest` (unit: загрузка, дефолты,
env > file, нулевые/отрицательные/невалидные значения),
`UpstreamTimeoutsTest` (E2E: зависший upstream прерывается по env-значению,
медленный чанковый стрим переживает меньший response timeout, задержанный
первый байт переживает меньший idle timeout).

## Не входит

Retry, circuit breaker, per-route таймауты, таймауты plugin-вызовов.

## Рекомендуемые решения внутри issue

- Названия: `vigilant.upstream.connect-timeout`, `write-timeout`,
  `response-timeout` (env: `VIGILANT_UPSTREAM_CONNECT_TIMEOUT` и т.д.).
- Модель для стримов: response timeout как время до первого байта плюс
  idle-таймаут между чанками, если Armeria поддерживает; иначе документально
  большой response timeout с явной оговоркой.
