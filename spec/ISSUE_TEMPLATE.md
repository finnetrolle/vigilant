# Канонический шаблон issue

Классификация и readiness принадлежат
[WORK_ITEMS](WORK_ITEMS.md#risk-based-readiness). Этот документ - единственный
owner формата scope lock, context sources и optional papercut tags. Учебные
[примеры](examples/issue-authoring.md) показывают заполнение, не вводя правил.

## Основа

Скопировать блок в owning issue, заменить placeholders. ID и связи оформить
по [правилам каталога](WORK_ITEMS.md#идентификаторы-и-связи); необязательные Epic,
fulfilled prerequisites и papercut tags удалить, если они не применимы.
Для `Low` дополнительных разделов риска нет. Для `High` заменить разделы
«Результат» и «Не входит» одним [scope lock](#scope-lock), либо одной ссылкой
на его owning epic section: не копировать одно решение в два документа.
Критерии leaf issue остаются её собственными проверяемыми обязательствами.

```markdown
# <ID>: <один наблюдаемый результат>

- **ID:** `<ID>`
- **Тип:** Issue
- **Статус:** Draft
- **Приоритет:** <приоритет>
- **Epic:** <ссылка на owning epic, только для child issue>
- **Зависит от:** <ссылки на unfinished hard dependencies или нет>
- **Выполненные предпосылки:** <ссылки на published capabilities>
- **Блокирует:** <ссылки или нет>
- **Оценка:** <инженерные дни>
- **Уверенность:** <уровень>
- **Архитектурный риск:** <Low или High> - <одна короткая причина>

## Результат

<Наблюдаемый результат локального изменения.>

## Context sources

- `<repository-relative-path>#<exact-anchor>`

## Papercut tags

- `<exact-tag>`

## Критерии готовности

- [ ] <Вход/состояние -> наблюдаемый результат; независимый oracle.>

## Проверки

<Точные команды и обязательные наблюдения.>

## Не входит

- <Явная граница изменения.>
```

<a id="scope-lock"></a>

## Scope lock: только High

Вставить следующий блок в owning issue или epic. Он содержит ровно семь
смысловых частей. Для каждой рассмотренной более сложной альтернативы указать
причину отказа. Подтверждение относится к этой границе решения: указать явное
подтверждение владельца или точную ссылку на согласованный источник.
Placeholder, предположение агента или собственное «approved» без основания
не являются подтверждением. Незакрытые части явно помечать в `Draft`.

```markdown
## Scope lock

1. **Наблюдаемый продуктовый результат:** <что получает пользователь>.
2. **Минимальное достаточное решение:** <достаточная граница механизма>.
3. **Обязательные свойства результата:** <точные ограничения и гарантии>.
4. **Явные non-goals:** <что решение не включает>.
5. **Более сложные альтернативы:** <каждая альтернатива и причина отказа>.
6. **Условие пересмотра:** <наблюдаемый сигнал для нового решения>.
7. **Подтверждение:** <владелец и явное подтверждение или ссылка на согласованный источник>.
```

Если lock находится в epic, leaf issue вместо копии содержит Markdown-ссылку
на его точный anchor. Leaf-specific ограничения сохраняются в её criteria;
если они меняют согласованную границу, owning lock пересматривается.

<a id="context-sources"></a>

## Context sources и papercut tags

Раздел `Context sources` перечисляет только необходимые внешние для issue
разделы repository documents. Каждая запись - один точный путь от корня
репозитория с существующим Markdown anchor, в inline code, например:

```markdown
## Context sources

- `spec/WORK_ITEMS.md#risk-based-readiness`
- `docs/agent-workflow.md#work-item-completion`
```

Выбирать узкий owning section, без glob, приблизительного heading, полного
документа без anchor или копии его текста. Relative Markdown navigation links
в issue остаются обычными ссылками относительно issue-файла; они не заменяют
эти repository-relative declarations. При отсутствии внешнего контекста явно
писать `нет`. Содержимое самой issue не перечислять как внешний source.
Автор проверяет существование каждого пути и anchor запуском
`rtk proxy ./scripts/task-context <ID>` по [контракту команды](../docs/task-context.md#contract).
Раздел обязателен для packet, в том числе у legacy issues; его добавление
не пересматривает frozen scope или readiness. H1, overlapping selections,
glob, path traversal и percent-encoded aliases не принимаются.
ATX/Setext headings используют exact Unicode slug с suffix для повторений.
Explicit `<a id="name"></a>` ставится отдельной строкой непосредственно перед
heading; между ними допустимы пустые строки. Fenced examples не создают anchors.
Если scope lock принадлежит epic, его owning section обязательно объявить
здесь: обычная Markdown-ссылка сама по себе не раскрывает source.

Необязательный `Papercut tags` содержит exact tags из journal, по одному в
inline code на строку. При отсутствии применимых tags удалить весь раздел;
не подставлять приблизительные tags и не копировать journal в issue.
